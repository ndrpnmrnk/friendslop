# Публикация Friendslop: тесты отдельно от боевой игры

Решение автора от 30.10.2026. Обязательно для любой ИИ, разработчика и автоматизации.

## Главное правило

Все промежуточные изменения отправляются в `main` и проверяются на GitHub Pages:
https://ndrpnmrnk.github.io/friendslop/

Публикация для всех игроков разрешена только после явной команды автора для конкретного обновления («выкатываем», «в релиз»). Тогда проверенные изменения переносятся в `release`; боевой сайт:
https://friendslop-6h1.pages.dev/

Обычный запрос исправить ошибку, продолжить работу, сохранить код или обновить тестовую игру не разрешает боевой деплой. Не выполнять `wrangler deploy`, `wrangler versions upload`, запуск боевого workflow или продвижение `release` без такой команды. Не отправлять каждый мелкий коммит на Cloudflare.

## Что проверено в репозитории, а что требует настройки

- `.github/workflows/deploy.yml` собирает сайт и публикует GitHub Pages из `main`. Этот workflow не вызывает Cloudflare.
- Клиент `src/net/net.js` по умолчанию подключается к общему серверу комнат `friendslop-rooms` на Cloudflare. Поэтому онлайн-игра с тестового сайта тоже использует Worker / Durable Objects.
- В прежнем `docs/ONLINE_PLAN.md` сервер комнат был описан как автоматически обновляемый из `main`. На скриншоте автора у обоих Cloudflare-проектов видны недавние изменения. Это указывает на необходимость проверить отдельно боевые и preview-триггеры; сам скриншот не показывает их точные параметры.
- Приведённые ниже параметры - требуемая схема. Наличие этой инструкции в GitHub само по себе не изменяет настройки Cloudflare Dashboard. Не заявлять, что автосборки отключены, пока это не проверено в кабинете или API.

## Рекомендуемая схема: обе боевые части только из release

| Компонент | Ветка | Автосборки |
| --- | --- | --- |
| Тестовая игра GitHub Pages | `main` | Существующий GitHub Actions |
| Боевой сайт Cloudflare Pages `friendslop` | `release` | Только production; preview выключен |
| Боевой Worker `friendslop-rooms` | `release` | Только production и только при изменении серверных файлов |
| Локальный Worker для разработки | Локальный checkout | `cd worker && npm run dev`, без публикации на Cloudflare |

### Однократные настройки в Cloudflare Dashboard

1. **Pages `friendslop`**: открыть Settings → Builds / Builds & deployments → Branch control. Production branch = `release`; Preview branches = **None**. Сохранить. Автоматический production-деплой можно оставить включённым: он будет происходить только при продвижении `release`, которое отдельно разрешает автор.
2. **Worker `friendslop-rooms`**: открыть Settings → Builds / Build → Branch control. Production branch = `release`; **Enable Preview Builds = Off** (в старом интерфейсе - Non-production branch builds). Сохранить.
3. У Worker сохранить Root directory = `worker`, Deploy command = `npx wrangler deploy`. Имя проекта `friendslop-rooms` должно совпадать с `name` в `worker/wrangler.toml`.
4. У Worker настроить **Build watch paths**, Include = `worker/*`, Exclude оставить пустым. Пути задаются относительно репозитория. Так изменения районов, интерфейса, звука и документации не запускают сборку сервера. При появлении внешних файлов, от которых зависит сервер, добавить их явно.
5. При необходимости аналогично исключить из сборок Pages `docs/*`, `AGENTS.md`, `CLAUDE.md`, `NEXT_UPDATE.md`, `README.md`; следить, чтобы изменения игровых исходников, ассетов, зависимостей и конфигурации сборки продолжали учитываться.

Достаточно один раз связать проекты с GitHub. Переподключать Cloudflare после каждого обновления не нужно. Переключение production branch не является разрешением немедленно переносить `main` в `release`.

### Проверка настроек

- После следующего обычного изменения клиента в `main`: GitHub Pages обновился, у обоих Cloudflare-проектов не появилась новая сборка.
- После документационного коммита: сборок Cloudflare тоже нет.
- Только после команды автора и продвижения `release`: Pages публикует проверенную игру; Worker собирается лишь при изменениях, попавших в его watch paths.
- Если Cloudflare всё ещё собирает `main`, проверить preview-триггер, production branch и внешние Deploy Hooks. Фильтра по файлам без фильтра по ветке недостаточно.

## Как тестировать онлайн

GitHub Pages размещает файлы игры, но не запускает наш WebSocket-сервер комнат. Для онлайна по-прежнему нужен уже работающий Worker.

Если изменился только клиент и протокол совместим, игру с GitHub Pages можно проверять на существующем Worker без его повторной публикации. Такие сеансы расходуют обычные сетевые квоты Cloudflare, но сами по себе не запускают сборки.

Если меняется сервер или несовместимый протокол, сначала проверять его локально (`cd worker && npm run dev`; локальному клиенту можно передать `?server=ws://127.0.0.1:8787`). Локальный адрес недоступен другу через интернет. Для удалённой проверки серверных изменений можно отдельно согласовать тестовый Worker и публиковать его вручную по необходимости; он должен иметь отдельные комнаты / Durable Objects и не затрагивать боевой Worker. Отдельный Worker в том же аккаунте не даёт отдельный бесплатный лимит аккаунта.

## Выпуск после подтверждения автора

1. Уточнить конкретный проверенный коммит / версию. Не захватывать автоматически более новые непроверенные параллельные изменения из `main`.
2. Проверить совместимость клиента и Worker. Если сервер менялся, заранее определить порядок публикации и поведение существующих комнат.
3. После явного разрешения продвинуть `release` до согласованного коммита обычным fast-forward. Если ветки разошлись, не применять force push; сначала разобраться с расхождением.
4. Проверить успешность нужных Cloudflare-сборок, адрес игры и соответствие опубликованного коммита. Если Worker не менялся, его повторный деплой не нужен.
5. Зафиксировать версию и результаты проверки. Не обещать синхронную атомарную публикацию Pages и Worker: это разные сервисы.

## Альтернатива: полностью ручной Cloudflare

Для максимального контроля отключить автоматические production- и preview-сборки Pages, а Worker отключить от Workers Builds. Действующие опубликованные версии при этом продолжают обслуживать игроков. Сам сайт и Worker удалять не нужно.

Выпускать только по команде автора через отдельный ручной GitHub Actions (`workflow_dispatch`) или Wrangler: собирать в GitHub / локально, загружать готовый `dist` в Pages и изменённый Worker. Это позволяет убрать сборки из Cloudflare Builds, но требует однократной безопасной настройки токена и секретов GitHub. Токены не хранить в репозитории. Эта альтернатива описана, но не внедрена и не активирована.

Замена `wrangler deploy` на `wrangler versions upload` не решает задачу экономии сборок: сборка по-прежнему выполняется, просто версия не становится активным деплоем.

## Разные квоты - разные действия

- Cloudflare Pages Free: 500 сборок в месяц.
- Workers Builds Free: 3 000 минут сборки в месяц. На скриншоте автора показано 59 / 3k именно этих минут, а не 59 игровых запросов или 59 из 500 сборок Pages.
- Worker / Durable Objects: отдельные квоты реальной работы сервера во время игры. Их нельзя обнулить переносом статического сайта на GitHub Pages.
- У GitHub Pages и Actions есть собственные ограничения. Не называть тестовый хостинг «безлимитным».

Тарифы и интерфейс могут меняться; перед настройкой сверять официальную документацию.
